rudnik-review

One formatter and one review for every language you write, inside the agent you already use.

Why it exists

Your agent writes code faster than anyone can read it, and fast code leaves small things behind: an eval on user input, a secret pasted into a test, an import nobody uses. None of it is dramatic, and all of it adds up. rudnik-review formats what you change and stops a change that brings a new defect, at the three moments it matters. Code that was there before never blocks you, so it does not nag you about the past.

The first ten minutes

You need git with access to this repository and uv; macOS, Linux and Windows work, less the analysers the README's Needs exclude. Install once a machine:

uv tool install git+https://github.com/ivansttt/rudnik-review

With ssh keys: git+ssh://git@github.com/ivansttt/rudnik-review.

Then, once in each clone:

rudnik-review init           # wires Cursor, Claude Code, Codex, JetBrains, git commit
rudnik-review init github    # the pull request's check, once a repository
rudnik-review setup          # the tools your languages need

Commit the files init wrote. The first of you also runs rudnik-review fmt --all and commits that on its own, so whole files are reformatted once and not inside your changes. Claude Code: accept the rudnik-review plugin it offers (init claude where init saw none). Codex: open /hooks once and trust its hook, and again when it changes.

What it looks like when it stops something

Say you ask the agent for a calculator endpoint and it writes return eval(expression). When it tries to finish, it gets this back instead of a green light:

error api/calc.py:12 ruff S307: Use of possibly insecure function; consider using `ast.literal_eval` 7c2e…

It does not stop there: it parses the expression properly, the check runs again and is quiet, and the agent finishes. The unused import two lines up came back as a warning, which you may mend or leave. The code at the end of the line is the finding's fingerprint (shortened here). If you are sure a finding is wrong, don't work around it: answer NOTE-WRONG: <fingerprint>: <why> in the agent's reply.

The same holds elsewhere. In JetBrains, files are formatted when you save, Junie has check and explain as tools, and for AI Assistant you paste the one line init printed into its MCP settings. git commit is refused while what you staged holds a new error, and the pull request's rudnik-review check fails on one and shows each finding on its line.

What one check does

That second pair of eyes, asked when an agent finishes and on check --llm, never at a commit or the pull request, is another vendor's model, through the CLI you are signed in to (Codex or Claude Code), never a key from us; with neither, it is skipped.

By hand

rudnik-review check                  # what this branch adds; an error stops you
rudnik-review fmt                    # format the files you changed
rudnik-review check --format sarif   # .rudnik/review.sarif, which a JetBrains IDE opens
rudnik-review update                 # the next release and its tools

Python, JavaScript and TypeScript, Go, Rust, Java, Kotlin, C#, C and C++, Swift, shell, SQL, YAML, TOML, Terraform, Dockerfiles and GDScript are covered, and every file is searched for secrets. The README lists each language's formatter, analysers and what they need, and what to do when something is off.
